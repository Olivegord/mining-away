# Profile persistence contract

`src/Persistence.lua` is the storage boundary. The runtime must select the adapter explicitly. `Persistence.dataStore(dataStore)` uses Roblox `UpdateAsync`; `Persistence.previewAdapter(namespace)` uses an isolated ephemeral namespace and reports `Preview — not saved across server restarts`. DataStore failure never switches a live session to preview or creates a replacement default profile.

A stored value is an envelope with `storageVersion = 1`, a monotonic `revision`, the Profile schema document under `data`, a bounded internal transaction-receipt array, and `lock = {owner, token, expiresAt}`. Profile and envelope schema versions are separate. A valid legacy raw Profile document is migrated once. Malformed data, unknown future schemas and corrupt locks are rejected without overwriting the stored value. A genuinely absent value is the only path that invokes `newProfile`.

Each server must supply a unique owner, normally its job identity plus a generated GUID. Loading atomically acquires a tokenized lease. Every write checks that exact owner/token and the expected revision. Another server may acquire an expired lease; its new token fences the old server's stale save. The manager defaults to a 180-second lease and three ordered attempts with short bounded backoff. The runtime must autosave well before lease expiry, stop gameplay on an unhealthy session, save/release on leave, and await bounded final release/reconciliation on shutdown.

`manager:transaction(session, id, mutate)` clones session data, executes the non-yielding pure mutation once, validates it, then atomically commits that candidate and its result receipt. Repeated `UpdateAsync` callback execution cannot reroll its offer or random target. Local `session.data` is replaced only after durable success. The runtime must pause all owner data mutations while `session.busy`; a reference to the old data table must be refreshed after a successful transaction or reconciliation.

The mutation returns a truthy serializable result on success. Returning `nil/false, error` rejects the operation without a write. The transaction returns `true, result` only when its durable receipt is known. Replaying the same recent ID returns its original result without invoking the mutation. This internal ledger is bounded (48 receipts by default), so domain actions additionally validate monotonic run/pack/offer identities and keep their own bounded receipts; arbitrary ancient requests must not become valid just because a storage receipt aged out.

A service exception may occur after the service committed. Exhausted retries leave `session.readOnly = true`, the previous local data unchanged, and the exact pending transaction ID recorded. `manager:reconcile(session)` discovers whether that ID committed. A confirmed committed receipt adopts authoritative stored data; a confirmed absent receipt at the unchanged revision preserves the pre-transaction local data, including legitimately earned dirty cargo. It never adopts the rejected staged mutation. Session takeover or revision conflict fails closed. The server must not publish pack/prestige success, reroll an offer, or grant a permanent drone while an outcome is unresolved.

`save` persists the current session state through the same serial gate and renews the lease. `release` saves and removes the lease in the same atomic update. A lost response to release is reconciled by its receipt even though the lease was removed; repeating release on a closed session cannot affect a new session's lease.

Validation executed in the cloud: 28 deterministic tests using the real persistence manager and a fault-injecting UpdateAsync double, including pre/post-commit failures, callback repetition, crash/reload, session takeover, revision conflict, final-save failures, migration rejection, bounded receipts and preview isolation. Luau compilation and standalone analysis pass. No live DataStore access or Roblox engine test was executed for this module; the runtime must keep that limitation explicit.

Signed local Studio identities (including -1 and -2) are accepted only by an explicitly labeled Preview adapter. The real DataStore adapter requires a positive account ID. Preview and production identity policies cannot be selected by client input.
